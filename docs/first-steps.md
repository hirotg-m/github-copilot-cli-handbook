# GitHub Copilot CLI を初めて使うときの実践ステップ

このガイドでは、`copilot` コマンドを実行できる状態から、GitHub Copilot CLI に安全に作業を任せる感覚をつかむまでの手順を説明します。最初は本番環境や重要なブランチではなく、内容を理解している小さなリポジトリで試してください。

## 1. 作業用のブランチを作成する

作業対象のリポジトリで、現在の変更とブランチを確認します。未コミットの変更がある場合は、内容を把握してから進めてください。

```bash
git status
git switch -c copilot-cli-first-steps
```

既存の作業ブランチを汚したくない場合は、別のサンプルリポジトリを使います。

## 2. Copilot CLI を起動してリポジトリを理解させる

リポジトリのルートで起動します。

```bash
copilot
```

初めて開くディレクトリでは、信頼確認が表示されます。Copilot CLI はファイルの読み取り、変更、コマンド実行を提案するため、内容を信頼できるリポジトリでだけ許可してください。

最初はファイルを変更しない質問から始めます。

```text
このリポジトリの目的、主要なディレクトリ、実行方法を説明してください。ファイルは変更しないでください。
```

回答に含まれるファイル名やコマンドを自分でも確認し、リポジトリの理解が正しいか確かめます。期待と異なる場合は、次のように範囲を指定して質問し直します。

```text
README.md と docs/ だけを読んで、このドキュメントの対象読者と構成を説明してください。変更やコマンド実行はしないでください。
```

## 3. 調査を具体的な作業に分解させる

次に、実際に行いたい作業を、変更前の調査と実施に分けて依頼します。例えば、手元の課題を使って次のように入力します。

```text
「<実現したいこと>」に対応したいです。まず関連するファイルを調査し、変更案、影響範囲、確認方法を示してください。まだファイルは変更しないでください。
```

`<実現したいこと>` は、具体的に置き換えます。最初の練習には、誤字の修正、README への手順追加、設定値の説明追加など、小さく戻しやすい作業が向いています。

提案を確認するときは、少なくとも次を確認します。

- 変更対象のファイルが目的に合っているか
- 既存の書式や命名規則に従っているか
- 実行するコマンドと、そのコマンドが変更する対象
- 確認方法が変更内容に対応しているか

不明な点があれば、実施前に質問します。

```text
提案した各ファイルを変更する理由と、変更しない場合の影響を説明してください。
```

## 4. 小さな変更を依頼して確認する

変更内容に同意できたら、対象と完了条件を明示して依頼します。

```text
提案どおりに README.md の誤字を修正してください。ほかのファイルは変更せず、変更後に差分を表示してください。
```

Copilot CLI がファイル変更やコマンド実行の許可を求めたら、コマンドと対象パスを読んでから許可します。意図しない対象や破壊的な操作が含まれる場合は拒否し、範囲を絞って指示し直してください。

完了後は、対話セッションの外で差分を確認します。

```bash
git diff --check
git diff
git status
```

`git diff --check` で空白エラーを確認し、`git diff` で意図した変更だけが含まれることを確認します。意図しない変更があれば、すぐにコミットせず、変更理由を Copilot CLI に質問するか、必要な部分だけを手動で直します。

## 5. 確認コマンドを実行する

変更に対応する最小の確認を依頼します。リポジトリにテストやリンターがない場合は、確認できないことを明確にします。

```text
今回の変更に必要な最小の確認を実行してください。利用できる確認手段がない場合は、その理由と手動で確認した内容を報告してください。
```

実行前にコマンドを確認し、依存関係の追加、外部サービスへの接続、広範囲なファイル変更を伴う場合は、必要性を確認してから許可します。失敗した場合は、エラー全文、原因の候補、次に試す最小の対応を尋ねます。

```text
失敗の原因を調査してください。ファイルは変更せず、再現手順と最小の修正案を示してください。
```

## 6. セッションを整理して変更を残す

作業の区切りで、行ったことと残作業を要約させます。

```text
このセッションで変更したファイル、実行した確認、その結果、残っている注意点を簡潔にまとめてください。
```

内容を確認したら、まず Copilot CLI にコミットメッセージを提案させることもできます。意図しないコミットを避けるため、提案だけを求め、コミットを実行しないことを明示します。

```text
現在の git diff を確認して、変更内容に合う Conventional Commits 形式のコミットメッセージを3案提案してください。コミットは実行しないでください。
```

コミットする変更をステージ済みの場合は、`git diff --staged` を対象にします。

```text
git diff --staged の内容から、日本語の簡潔なコミットメッセージを提案してください。コミットは作成しないでください。
```

提案から選んだメッセージが差分に合っていることを確認したら、必要に応じて自分でコミットします。

```bash
git add README.md
git commit -m "docs: README の誤字を修正"
```

コミットするファイルは、必ず `git status` と `git diff --staged` で確認してから選びます。Copilot CLI にコミット作成を依頼する場合も、コミット対象とメッセージを確認してから実行してください。

## 7. 次に試すとよい依頼

小さな変更に慣れたら、次の順で範囲を広げると安全です。

1. エラーやログを渡し、原因候補と調査手順だけを求める
2. テスト失敗を再現し、修正案と追加・更新すべきテストを求める
3. 小さな機能変更について、実装、確認、差分レビューを順に依頼する
4. プルリクエスト用に、変更内容、確認結果、注意点を要約させる

各段階で、依頼の範囲、変更してよいファイル、完了条件を明示してください。Copilot CLI の提案は確認の代わりにはならないため、差分と実行結果を確認してから採用します。

## 8. 困ったとき

### 予想より多くのファイルを変更しようとする

許可を拒否し、対象を限定して依頼し直します。

```text
変更対象は src/example.ts と src/example.test.ts だけにしてください。それ以外が必要な場合は、変更前に理由を説明してください。
```

### 回答が一般的で、リポジトリに合っていない

読んでよいファイルや確認すべき観点を指定します。

```text
package.json、README.md、src/ を確認して、このリポジトリで使われているテストコマンドだけを教えてください。実行や変更はしないでください。
```

### 実行するコマンドが不安

コマンドの目的、変更対象、取り消し方法を先に尋ねます。

```text
そのコマンドが何をするか、変更するファイルや外部サービス、失敗時の影響を実行前に説明してください。
```
